# Release Evidence Standard

Status: CONTROLLED

## Purpose
Defines the minimum evidence required to claim implementation maturity.

## Evidence states
- IMPLEMENTED: code/config exists at an identified commit.
- VERIFIED: relevant automated/manual checks pass against that commit/artifact.
- PRODUCTION: the exact verified artifact is deployed to the declared production environment and independently verified there.

A document, screenshot, green badge, or local test alone cannot prove PRODUCTION.

## Required chain
For a release claim retain, where applicable: source commit SHA; PR; required CI run IDs and conclusions; dependency/build lock evidence; artifact digest/signature/provenance; release tag; deployment workflow/run; target environment identity; migration result; health/smoke result; observability snapshot; approval record; rollback target; timestamp and operator/automation identity.

## Integrity
Evidence must be generated by or directly reference the system being asserted. Manually copied summaries are secondary evidence. Secrets, credentials and customer-sensitive data must be redacted without destroying the fields needed for verification.

## Failure handling
Missing, contradictory, stale or unverifiable evidence lowers the state to the highest state that can actually be proven. Failed checks may not be hidden, deleted, or reclassified as PASS.

## Retention
Release evidence should be retained at least for the supported lifetime of the release plus the applicable security/audit retention period. External certifications are recorded separately and must not be inferred from repository tests.
